# Feature Context: Deployment Guidance

## Feature Boundary

This feature changes the supported operator contract after the managed-copy pipeline exists. It rewrites the Evangelize source of truth, regenerates every harness variant through the propagator, and reconciles active setup and troubleshooting guidance so supported user-global deployment invokes or verifies managed copies instead of creating or repairing runtime symlinks or junctions.

This feature does not define destination paths, ownership evidence, collision behavior, staging, replacement, or pruning. Those behaviors must be reused from `02-propagation-convergence`, `03-cross-platform-destinations`, and `04-managed-copy-reconciliation`. It also does not remove legitimate discussion of hostile symlinks, Git-hook links, plugin-cache links, package-managed links, debug pointers, or historical behavior.

## Verified Existing Contracts

- `.github/agents/evangelize.agent.md` is the source of truth. The Claude, Codex, and OpenCode files listed above are generated by `scripts/propagate_master_assets.py` and carry generated markers.
- The current Evangelize source explicitly instructs Claude, Codex, and OpenCode runtime symlink maintenance, contains POSIX and PowerShell link recipes, and treats link existence/targets as readiness evidence.
- `propagate_once`, `watch_loop`, and `main` are verified existing entry points. The propagator returns structured integer counters and already renders all Evangelize variants.
- The generated repository roots are `claude/`, `codex/`, and `opencode/`. User-global deployment must consume these generated outputs, never `.github/` sources directly.
- `HARNESS_SETUP.md` and `docs/TROUBLESHOOTING.md` are active operational surfaces, not merely incidental mentions: they instruct users to create or recreate runtime links.
- The Phase explicitly preserves unrelated Git-hook link guidance and legitimate security/historical discussion. A repository-wide ban on the words `symlink` or `junction` would violate scope.
- Native Windows and WSL require separate runs and separate evidence. Unavailable evidence is `NOT RUN`, never inferred success.

## Architectural Decisions

### Source-First Regeneration

Edit only `.github/agents/evangelize.agent.md` for Evangelize behavior, then run the established propagation workflow until it reaches the bounded fixed point supplied by Feature 2. Generated variants must be compared to their platform renderers or existing parity conventions; direct edits to generated variants are prohibited.

### One Canonical Managed-Copy Workflow

Evangelize and setup guides should reference the settled public orchestration/deployment API from Features 2 and 4 rather than duplicating path resolution, ownership classification, collision handling, replacement, or pruning algorithms in prose. The exact API symbol is not yet verified in the current codebase and must remain `[PROPOSED - name TBD]` until upstream implementation settles it.

The operator sequence is fixed by the Phase: repository convergence, reviewed destination preflight, managed-copy deployment, per-harness reconciliation, and runtime discovery. Completion reporting must preserve partial results and must not claim a failed or unavailable harness passed.

### Operational-Intent Documentation Audit

Regression protection should classify instructions by operational intent and supported surface. It must reject commands or procedures that create, repair, recommend, or validate runtime links for generated assets, including POSIX `ln -s`, PowerShell `New-Item -ItemType SymbolicLink`, Windows `mklink`/junction procedures, and prose equivalents.

Allowlisted contexts must remain narrow and reviewable: hostile-link security analysis, historical Phase records, unrelated Git-hook installation, package/plugin-managed links, and explicit statements that runtime links are retired. Do not use a broad file exemption merely because a document contains legitimate link terminology.

### Active-Surface Classification Before Editing

Build a complete inventory of operational link instructions before changes. At minimum, classify every file in the plan plus `HARNESS_SETUP.md` and `docs/TROUBLESHOOTING.md`. For `codex/PILOT_SLICE_PLAN.md`, decide whether it is a supported procedure or historical record; if retained as history, label it clearly enough that users and regression tests cannot mistake its commands for current setup guidance.

### Observability and Readiness

Reuse upstream structured propagation, collision, copy, freshness, and runtime-discovery statuses. Normal-path documentation should not introduce per-file chatter. A readiness summary must report each harness independently and use `NOT RUN` for unavailable native Windows or WSL evidence. Full cross-platform GO is impossible while any required platform is `NOT RUN` or failed.

## Constraints and Edge Cases

- Do not replace link recipes with ad hoc `cp`/`Copy-Item` recipes that bypass ownership metadata, collision review, convergence, staging, or safe pruning.
- Do not describe existence of a regular file as sufficient proof. Verification includes freshness, expected roster coverage, collision outcome, per-harness deployment status, and fresh-session runtime discovery.
- Preserve the distinction between repository-generated copies and user-global managed copies.
- Include agents, commands, skills, profiles, supported settings/hooks outputs, and learning assets in the operational audit where the upstream deployment roster supports them.
- Treat stale watcher processes as unsafe evidence; restart long-running propagation watchers after propagator changes.
- A failed harness must remain failed/partial, skip its destructive reconciliation, and not be masked by another harness's success.
- A platform unavailable to the current test environment must be reported as runner-constrained or `NOT RUN`; static prose assertions cannot substitute for live runtime evidence.
- Normalize whitespace or parse the relevant section when asserting prose obligations. Whole-document literal checks can pass from an unrelated occurrence and hard-wrapped prose can produce brittle false results.
- Negative documentation fixtures must prove the guard fails when prohibited operational language is inserted. Retaining a passing fixture alone does not prove the regression guard bites.
- Do not update Phase 01, Phase 02, or Phase 07 status lines in this feature.

## Relevant Learnings

### Generated assets and convergence

From `.github/learnings/cross-phase-decisions.md`:

- Generated roots are `claude/`, `opencode/`, and `codex/`; user-global paths are not repository-generation destinations.
- Generated Markdown and TOML use type-specific markers, so checks should use the established renderers and marker contracts rather than assume byte identity with sources.
- A stale `--watch` process can retain old propagation logic. Restart it after propagator changes before collecting evidence.
- A single propagation pass does not prove convergence after reclassification. Run until every counter is zero before deployment or generated-output verification.

### Regression checks for generated and prose surfaces

From `.github/learnings/review-learnings.md`:

- Propagation regression tests must cover every generated output and compare each harness render with the source renderer; an existence-only check can miss stale variants.
- Whole-document literal assertions are inert when the token occurs elsewhere. Scope checks to the section or obligation they protect.
- Normalize whitespace for sentence-level prose assertions so line wrapping does not control the verdict.
- Prove a prose regression guard with targeted mutation/negative fixtures; a green unmutated test is not sufficient evidence.
- Do not add broad exemption lists when a sweep finds a legitimate token. Classify the context or derive the allowlist narrowly.

### Unrelated learnings

The retained-evaluation identity guidance in `.github/learnings/project-learnings.md` and review-ledger lifecycle guidance do not apply to this deployment-documentation feature.

## Discovery Delta

### Required companion files omitted from the plan scope

Repository discovery found two active supported surfaces that contradict the plan's stated goal if left unchanged:

- `HARNESS_SETUP.md` contains executable cross-harness runtime-symlink procedures, Windows Developer Mode/elevation guidance, runtime-link verification, and the claim that links make updates immediately visible.
- `docs/TROUBLESHOOTING.md` instructs users to recreate those links through `HARNESS_SETUP.md`.

Both files should be added to the plan and manifest key-files lists before execution. This context and the tasks below treat them as required `(verify)` scope, but the Plan Expander has not modified the plan.

### Accepted classification risk

`codex/PILOT_SLICE_PLAN.md` is verified to contain executable link-installation and `readlink` verification steps. The plan already identifies its active-versus-historical status as unverified. Implementation must settle and document that classification; silently retaining executable instructions without a historical warning would fail AC4–AC7.
